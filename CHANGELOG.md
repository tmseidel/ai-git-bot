# Changelog

All notable changes to AI-Git-Bot are documented in this file.

The format is inspired by [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project uses semantic versioning where practical.

## [Unreleased]

### Added

- Added **`linux/arm64` support for the Docker image**. `tmseidel/ai-git-bot:latest` and the versioned tags are now multi-arch manifest lists covering `linux/amd64` and `linux/arm64`, so Apple Silicon, AWS Graviton and 64-bit Raspberry Pi hosts pull a native image instead of failing or falling back to emulation. The build stage is pinned to `$BUILDPLATFORM` (the jar is architecture independent, so Maven never runs under QEMU), and the k6 install is now `TARGETARCH`-aware — the Grafana APT repository publishes no `arm64` packages, so `arm64` installs the official release tarball pinned by the `K6_VERSION` build argument. The publish workflow builds each architecture natively (`ubuntu-latest` / `ubuntu-24.04-arm`), pushes by digest and merges the results into one manifest list. Note that on `arm64` Cypress can only drive its bundled Electron browser; Playwright runs Chromium on both architectures. See [`doc/DEPLOYMENT.md`](doc/DEPLOYMENT.md#architectures).
- Added the **i18n Coverage** PR workflow (key `i18n-coverage`, category `DOCS`, opt-in per bot). It detects when a pull request's i18n changes (added keys, changed values, deleted keys) are not consistently reflected across locale files, then drafts the missing translations per locale with an LLM agent and removes stale keys, against a configurable **baseline locale** (`baselineLocale`, blank by default = auto-detect the reference file per bundle family; blank is persisted as-is and never reverts to a default). Supports both `messages_*.properties` resource bundles and `i18n/*.json` files, an operator-configured pattern scope (`includedFilePatterns`, defining both the files the bot inspects and the files it may change), an operator-editable system prompt (`system_prompts.i18n_coverage_system_prompt`, Flyway `V32`), the `commit-to-pr` / `offer-as-pr` / `ephemeral` lifecycle modes, and the `@bot regenerate-i18n <instruction>` slash command (trailing text is passed as extra translation guidance without changing the detection logic). Needs no deployment target or browser. See [`doc/PR_WORKFLOWS_I18N_COVERAGE.md`](doc/PR_WORKFLOWS_I18N_COVERAGE.md).
- Added the **README Sync** PR workflow (key `readme-sync`, category `DOCS`, opt-in per bot). It detects when a pull request's code changes make the project's Markdown documentation inaccurate or outdated, then updates, creates or removes the affected docs within an operator-configured pattern scope (`includedFilePatterns`, defining both the documentation the bot reads and the files it may change), and posts a short summary comment. Markdown-only; every changed file is constrained to the configured include patterns, and translated variants (e.g. `README.de.md`) are covered when the patterns match. Supports an operator-editable system prompt (`system_prompts.readme_sync_system_prompt`, Flyway `V31`), the `commit-to-pr` / `offer-as-pr` / `ephemeral` lifecycle modes, and the `@bot regenerate-readme <instruction>` slash command. Needs no deployment target or browser. See [`doc/PR_WORKFLOWS_README_SYNC.md`](doc/PR_WORKFLOWS_README_SYNC.md).
- Added the **Usage** page (`/usage`) that audits all AI provider interactions: a collapsible *AI usage* section (paginated/sortable table with Timestamp, AI-Integration, Session-ID, Input/Output tokens, Cache creation/read input tokens, Details, clearable via a *Clear all* button) and a collapsible *Errors* section (paginated/sortable table with expandable stack traces and JSON export), both filterable by timespan. Backed by the new `ai_usage_log` / `ai_error_log` tables (Flyway `V26`). All AI clients now report token usage and failed interactions (e.g. HTTP `401` responses) to the audit log, and the dashboard shows an **AI Errors** card (last 7 days, red when errors occurred) plus token totals from the audit log so AI errors are no longer invisible.
- Added **raw request/response payload auditing** to the AI usage log (opt-in). Every AI client now serializes the provider request and response bodies and stores them in the `raw_request` / `raw_response` columns of `ai_usage_log` (Flyway `V45`) when `ai-usage.raw-payloads-enabled=true`. The **Details** column on the Usage page opens a modal that displays the raw JSON payloads for debugging provider behavior, token accounting, and completions. Payloads are truncated to `ai-usage.max-raw-payload-length` (default 65535, matching the column size) so the schema limit is never exceeded. Serialization failures are swallowed so audit logging cannot break AI workflows.
- Added the **Unit-Test Author** PR workflow (key `unit-test-author`, category `TESTING`, opt-in per bot). It generates white-box unit tests for the files touched by a PR diff, runs them with the project's *own* test runner via the coding agent's existing execution mechanism (`ToolExecutionService`), commits the generated tests onto the PR branch and posts a result + coverage comment. Supports `maven`, `gradle`, `npm`, `pytest`, `go`, `cargo`, `dotnet`, `bundle`, `make`, `gcc` and `g++` (auto-detected by default), an operator-editable author system prompt (`system_prompts.unit_test_author_system_prompt`, Flyway `V23`), the `unit_test_suites` / `unit_test_cases` tables (Flyway `V24`), and the `@bot generate-tests` / `@bot rerun-unit-tests` slash commands. Unlike the `e2e-test` workflow it needs no deployment target or browser. See [`doc/PR_WORKFLOWS_UNIT_TEST.md`](doc/PR_WORKFLOWS_UNIT_TEST.md).
- Added per-bot **User Whitelist** (optional textarea on the bot edit form, backed by the new `bots.user_whitelist` column) that restricts which Git usernames may trigger AI-spending interactions — PR opens/syncs, `@`-mentions, inline review comments, review submissions, agent issue assignments and follow-up comments. Blank ⇒ everyone allowed (historical default); non-blank ⇒ strict allow-list enforced in `BotWebhookService#isCallerAllowed`. Recommended for bots installed on public repositories so unknown users cannot burn the bot's AI tokens.
- Added Dark Theme support with a toggle switch in the navbar.
- Added repository discovery metadata for search engines, LLMs, autonomous agents, and RAG systems.
- Added `llms.txt` as a concise LLM entry point.
- Added `llms-full.txt` as an expanded single-file project reference for larger context windows.
- Added `SECURITY.md` with vulnerability reporting guidance and operator security recommendations.
- Added `CITATION.cff` for GitHub citation metadata and software catalog indexing.
- Added `codemeta.json` with machine-readable software metadata for catalogs and crawlers.
- Added Maven project metadata for repository URL, SCM, license, issue tracker, and maintainer attribution.
- Added README discovery keywords and references to LLM/security/changelog metadata.
- Added the opt-in **`execute-code` agent tool**: the model can run a short Python program that calls the tools the run offers it — repository reads (`cat`, `rg`, `find`, `ctags-signatures`, …) joined by the bot's selected MCP tools on the coding, writer and agentic-review runs, and reachable on the agentic PR-workflow runs (readme-sync, i18n-coverage, unit-test-author, e2e) on the same terms — only once the bot's tool configuration selects it — and prints one compact result, so sweeping many files costs one round instead of many. The program runs in an empty throwaway directory with the repository reachable only through the tool surface (there is no checkout, so it cannot read files the bot's tool configuration never granted), and the built-in writes, the branch switch and the build tools are not callable from inside a program. It confines neither the filesystem nor the network, so it is **not** seeded into the Default tool configuration; where the deployment provisions the sandbox pool (the shipped image does) the program runs as one of a pool of per-execution identities instead of as the service user. See [`doc/BOT_TOOL_CONFIGURATIONS.md`](doc/BOT_TOOL_CONFIGURATIONS.md) and [`doc/DEPLOYMENT.md`](doc/DEPLOYMENT.md).

### Fixed

- Comment-based re-review requests on GitLab and Bitbucket no longer count the word "review" inside the bot's own mention. A bot named e.g. `reviewbot` is no longer triggered by `@reviewbot again`; the comment itself must ask for a review, e.g. `@reviewbot please review this again`. Gitea and GitHub are not affected, since they re-request reviews through the reviewer workflow.
- The bot no longer reacts to mentions of other users whose name starts with the bot's username (e.g. `@ai_bot2` or `@ai_bot.helper` for a bot named `ai_bot`) or to e-mail addresses such as `me@ai_bot.com`. Mentions are now matched as whole names on Gitea, GitHub and GitLab; `@ai_bot,` or `@ai_bot.` at the end of a sentence still count. A bot without a username is no longer treated as mentioned by every comment.
- AI integration token/worker-limit binding errors now show a safe validation flash message instead of a bare HTTP 400. Malformed routing/privacy values still return HTTP 400. Provider changes now require a new API key or explicit **Clear** for every provider, including switching to keyless Ollama or llama.cpp; saves also reject missing or unknown provider types. See [Editing an AI Integration](doc/USER_GUIDE.md#editing-an-ai-integration).

- **README Sync** now rechecks the original PR's state and workflow cancellation immediately before Git push, stopping publication when the PR is closed, merged, or cannot be confirmed open. Both `commit-to-pr` and `offer-as-pr` use this check; follow-up PR creation checks again. When publication stops or fails after the documentation diff has been captured, the workflow attempts to post that diff in a normal comment on the original PR, with an explicit notice for truncated previews. Providers must supply the required open-state information; missing state stops publication. The state check and push are not atomic, and comment delivery is best-effort. See [`doc/PR_WORKFLOWS_README_SYNC.md`](doc/PR_WORKFLOWS_README_SYNC.md).

- Fixed the **coding agent looping until its round budget was exhausted on issues that need no code change** (an explicitly read-only or question-only issue). A plain-language turn without tool calls and without a workspace change used to fall into an unbounded nudge loop: `attempt` was incremented on that path but never checked, so the run burned all 32 rounds (~20 minutes and ~370k prompt tokens on a CPU-only host) and ended with *"I was unable to produce a valid implementation"* — although the model had already answered correctly. The agent now asks once for either tool calls or a final answer, then either publishes that answer as an issue comment (new **`ANSWERED`** session status, Flyway **`V52`**, no branch and no PR) or fails fast. Prose-only turns no longer consume the validation retry budget, the NATIVE nudge no longer asks for a legacy JSON `runTools` envelope, and a file-changing round that leaves no diff still reports failure. Only file-changing tools count as an attempt, so a read-only request that runs the build or test suite to report on it can still end as an answer, and a reply that comes back empty or cut off at the token limit falls back to the complete answer the model gave before the nudge. Reported in [#417](https://github.com/tmseidel/ai-git-bot/issues/417), fixed by [#418](https://github.com/tmseidel/ai-git-bot/issues/418); design in [`doc/development-archive/answer-only-completion-architecture.md`](doc/development-archive/answer-only-completion-architecture.md).

- Fixed the **technical-writer agent discarding a run once its repository-context budget was spent**. A round whose tool calls arrived at the limit was dropped and the run ended with *"I need more context before I can continue"*, even when the model had already read most of what it needed. The writer now gets a **wrap-up round**: no tool is executed any more, every pending call is answered with *"not executed"*, and the model is told the budget is spent and asked for its final answer — a revised issue draft or the specific question it could not verify — with the following round producing that answer. The budget is configurable via **`agent.writer.max-tool-rounds`** / `AGENT_WRITER_MAX_TOOL_ROUNDS` (default `5`, next to the triage equivalent in `application.properties` and `docker-compose.yml`), and the output contract now names the limit so the model can spend its rounds deliberately. The answer round goes out **without tool descriptors**, because a local model that still sees them calls them instead of answering, and a run that reaches the round cap anyway now posts the *"more context needed"* comment instead of ending silently.

- Follow-up runs also **replay the previous native tool exchanges**: `conversation_messages` persists the assistant `tool_calls` payload and each tool row's `tool_call_id` (Flyway **`V53`**, both dialects), so a `continue` comment rebuilds the pairs the model saw instead of dropping the exchange; rows written before the migration are stripped exactly as before. Replay is shared by the loop, so **every** agent gets its earlier tool results back (the coding agent included) — those follow-up prompts are larger again by up to `agent.budget.max-tool-result-chars` per replayed result, and the results are the ones the run already truncated. A pair is replayed only when it is *complete*: an assistant turn whose announced calls were never answered — the shape a run leaves behind when it finishes on a tool-call turn, the writer's give-up branch included — is replayed as plain content instead, because both providers reject an unanswered `tool_calls` message. Replayed ids are rewritten to the `[a-zA-Z0-9_-]` alphabet every provider accepts (a local model hands out `cat:0`, which Anthropic rejects), the `[<id>]` review marker stored with a result is stripped, and orphaned or duplicated tool rows are dropped. See [`doc/AGENT.md`](doc/AGENT.md#how-a-writer-run-ends) and [`doc/development-archive/writer-agent-completion-plan.md`](doc/development-archive/writer-agent-completion-plan.md).
